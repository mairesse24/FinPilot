# Member 3: model behavior and next steps

## What the models predict

Three pooled LightGBM regressors estimate **USD of daily variable spending for one customer**. They are trained across customers, not separately for each person:

| Artifact | Prediction |
| --- | --- |
| `artifacts/models/lower.txt` | 10th-percentile daily spending estimate |
| `artifacts/models/median.txt` | 50th-percentile daily spending estimate |
| `artifacts/models/upper.txt` | 90th-percentile daily spending estimate |

The `.txt` files contain serialized decision trees, not prompts or source code. Leave them generated by training.

Inputs are previous spending lags and rolling statistics, weekday, day of month, month and an approximate payday-calendar feature. The model target covers groceries, transport, dining, shopping and other spending. The current model aggregates these categories; it does not separately forecast each category.

The same daily models run recursively to produce 7-, 30- or 90-day forecasts. Future checking balance is calculated separately:

```text
next checking balance = previous balance + scheduled income - scheduled bills - predicted variable spending
```

Health scoring, Guardian and economic pressure are rules and formulas, not trained predictive models. The optional OpenAI copilot explains calculations and can invoke approved tools. FinPilot does not train an LLM here. The lower/upper spending quantiles do not imply that the checking balance has a calibrated 80% confidence interval.

## Database responsibility

Member 3 does not need an external database connection for training or inference. Current inputs are local PNC CSVs; model trees, metadata, evaluation reports and demo JSON are written to local files. `analyze()` returns data in memory; it does not automatically save every prediction. A caller can persist its JSON output if needed.

For the shared web app, Member 2 should store users, accounts, transactions and bills in Supabase, enforce authorization, then call Member 3's functions with normalized records:

```text
Supabase -> Member 2 backend -> normalized customer + daily history
         -> Member 3 analyze()/simulate() -> JSON -> frontend
```

Member 2 can optionally save selected snapshots or alerts. Saving every forecast is unnecessary for the MVP. Model files belong with the deployed backend or in artifact/object storage, rather than as database table rows. A fresh hosted instance must receive the trained artifacts or explicitly use the documented baseline fallback; local files alone do not make shared user history durable.

## Next work, in order

2. **Broaden forecast validation.** Use multiple forecast origins, compare total 7/30/90-day spending, examine spending-day errors and irregular-income cases, and calibrate uncertainty. Current regular synthetic data makes headline accuracy optimistic.
3. **Strengthen features.** Add per-category trends and real customer-specific payday timing, keeping training and inference identical and all target features past-only.
4. **Refine the Guardian demo.** Check that a suggested action helps the specific risk; savings transfers and debt payments can worsen checking liquidity. Exercise scenarios against independent worked examples.
5. **Test live copilot integration.** Configure backend-only environment variables, make a small explicit test, and evaluate tool selection and explanations. Existing fake-client tests do not establish live API behavior; numeric-token matching alone does not prove correct reasoning.

Setting up Supabase remains Member 2's task. Member 3's immediate priority is a clear adapter and stronger model/decision validation.
